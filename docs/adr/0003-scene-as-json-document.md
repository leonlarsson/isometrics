# 0003. A dashboard is one JSON scene document, validated by Zod

## Context and problem statement

Dashboards must be editable by hand (inspector), possibly generated by AI, saved, imported/exported and rendered. All of these need to agree on one shape.

## Decision drivers

- Single source of truth that everything reads and writes.
- Safe to load untrusted input (files, AI output, old saves).
- Easy for agents to understand and extend.

## Decision outcome

The scene is a plain JSON document defined in `src/scene/schema.ts` with Zod (`SceneSchema`). Types are inferred from the schema (`TScene`, `TEntity`, …).

- **Every field has a default**, so old or partial documents parse.
- `version` is a literal. Breaking changes bump `SCENE_VERSION` and add a step to `parseScene` in `src/scene/migrate.ts`.
- All untrusted input goes through `parseScene()`.
- Entities are generic: `kind` names a part from the registry (ADR-0005), and part-specific settings live in `props`, validated by the part's own schema at render time. So adding a part never changes the scene schema.
- Ground units: 1 unit = 1 grid cell. Positions are `[x, z]`; rotation is degrees around Y.
- No runtime state (selection, camera, animation progress) is stored in the document.

### Consequences

- Good: the renderer is a pure function of the document; undo/redo is just snapshots (ADR-0009); AI generation becomes "emit a valid scene".
- Bad: part props are only loosely typed at the document level (`Record<string, unknown>`); invalid props fall back to defaults per key instead of failing loudly.
