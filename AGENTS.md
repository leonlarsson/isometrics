# AGENTS.md

Guide for AI agents (and humans) working in this repo.

## What this is

**Isometrics** lets non-technical users build animated 3D miniature worlds: low-poly scenes (buildings, vehicles, roads, bridges …) with floating data cards. **Data is a core pillar:** worlds exist to show data, and new features should stay data-capable where it's natural (ADR-0019). Users place, move, rotate, resize and recolour objects, draw roads and areas (water, grass, sand, plazas, raised land), label things with values, and switch to a clean View mode.

## Read first

- `docs/adr/README.md`: the architecture decisions and why. **Check the relevant ADRs before structural changes.**
- `src/scene/schema.ts`: the scene document, which is the single source of truth (ADR-0003).

## Commands (pnpm)

| Command | What it does |
|---|---|
| `pnpm dev` | Dev server on http://localhost:3000 (Vite + Cloudflare workerd) |
| `pnpm test` | Vitest unit tests (`src/**/*.test.ts`) |
| `pnpm e2e` | Playwright end-to-end tests (`e2e/*.spec.ts`) against the dev server; `pnpm e2e e2e/camera.spec.ts` for one file (see *Verifying visually*) |
| `pnpm typecheck` | Generate routes + `tsc --noEmit` |
| `pnpm check` / `pnpm check:fix` | Biome lint + format + JSX spacing check (`scripts/jsx-spacing.mjs`); `:fix` repairs what it can |
| `pnpm build` / `pnpm run deploy` | Production build / deploy to Cloudflare Workers (`pnpm deploy` without `run` is pnpm's own built-in command) |

Before finishing a change, run `pnpm check && pnpm typecheck && pnpm test`, and for UI changes the end-to-end specs for the area you touched (`pnpm e2e e2e/<area>.spec.ts`), adding or updating tests for what changed. CI (`.github/workflows/ci.yml`) runs lint, types and unit tests on every push to `main` and on pull requests; the end-to-end tests only run when started by hand from GitHub's Actions tab (Run workflow), split over three machines, so run the specs for what you changed locally.

## Layout

```
src/
  scene/      document model: Zod schema, parsing, road geometry, areas, path sampling, formatting, theme palettes (no React)
  parts/      procedural 3D parts, one file per part in a folder per palette category, + registry (definePart, PARTS)
  templates/  starter scenes
  editor/     Zustand store (history/undo), persistence, shortcuts, theme hooks
  render/     R3F scene: Viewport, CameraRig + CameraControls, EntityNode, TransformGizmo + KeyboardTransform, RoadMesh + road handles/draw tool, labels (3D side)
  ui/         DOM UI: the UI kit (Button, fields, List, Tabs, RailTabs, Tooltip, Menu, dialogs, toasts) and AppShell, Toolbar, PartsPalette, Outliner, Inspector (the properties editor and its tabs), LabelLayer, DetailSheet
  routes/     TanStack Start file routes (index = the editor, ssr: false; schema[.]json = the scene JSON Schema with every part kind and its props, ADR-0032; templates = the templates as complete worlds, ADR-0034, ADR-0083; parts = the public parts catalogue, ADR-0087; kit = dev-only UI kit page)
  styles.css  design tokens (light/dark) + base styles
scripts/      repo tooling (jsx-spacing check)
e2e/          end-to-end tests (Playwright), one spec per area, and their shared helpers (editor.ts)
docs/adr/     Architecture Decision Records
```

Dependencies point downward: `ui` → `render` → `editor` → `parts` → `scene` → `lib`. `scene/` must stay free of React and three.js so it remains testable and reusable on a server.

## Conventions

- **Naming (lint-enforced, ADR-0011):** type aliases `TName`, interfaces `IName`. Zod schemas are `NameSchema`, with inferred types `type TName = z.output<typeof NameSchema>`. Props interfaces are named after their component (`IEntityLabelProps`); a generic `IProps` is rejected.
- **Biome ≥ 2.6 is the only linter and formatter (ADR-0013).** Tabs, double quotes, line width 100. Run `pnpm check:fix` and let it order imports. Key rules: no `any`, no global `React.*` (import types directly), no unused variables or imports, `Number.parseFloat` over `parseFloat`. `useExhaustiveDependencies` is **off**, so don't add suppressions for it; unused `biome-ignore` comments fail the check.
- Import order (auto-fixed): packages → `#/` aliases → `../` → `./` → stylesheets last, with a blank line between groups.
- **Layout (ADR-0014):** every `if`/`else`/loop body is braced with the body on its own line (Biome `useBlockStatements`). Sibling JSX children (elements, fragments, `{expressions}`) are separated by a blank line, single-line ones included; inline text runs are exempt, and a `{/* comment */}` sits directly on top of the block it describes. Enforced by `scripts/jsx-spacing.mjs`, which is part of `pnpm check`, and fixed by `pnpm check:fix`.
- **Functions and exports (ADR-0015):** define every function as a `const` arrow function and use named exports only. No `function` declarations (not lint-enforced, so follow it by hand; Biome only catches function *expressions*), and no `export default` except in `*.config.*` files. Exception: route files in `src/routes/` keep `export const Route` first, followed by a hoisted `function` component. Arrow functions aren't hoisted, so define helpers before top-level code uses them, and write `<T,>` for unconstrained generics in `.tsx`.
- Imports use the `#/` alias for `src/`.
- **Keyboard (ADR-0016):** all shortcuts go through `@tanstack/react-hotkeys` (`useHotkey` / `useHotkeys`). Editor-wide ones live in `src/editor/useShortcuts.ts`; widget-specific ones use `target: ref`. Never add `keydown` listeners or `onKeyDown` props (not lint-enforced, so follow it by hand). Register `Shift+X` variants explicitly, and give each hotkey `meta: { name }`. The one exception is the clipboard: Ctrl+C / X / V use the browser's `copy`, `cut` and `paste` events in `editor/useClipboard.ts` (ADR-0068), the only way to use the clipboard without a permission prompt.
- The product name lives in one constant, `APP_NAME` (`src/lib/app.ts`). Never hard-code it in runtime code; derive variants from it (e.g. `APP_NAME.toLowerCase()`).
- Styling: CSS Modules next to the component, using **only tokens** from `src/styles.css`. 3D colours come from `scenePalettes` in `src/scene/theme.ts`; keep the two in sync (ADR-0007).
- **UI kit (ADR-0024, ADR-0025):** build every panel, bar and dialog from the kit in `src/ui/`: `Button`/`IconButton`/`IconButtonGroup`, the fields in `fields/` (one file per field: `TextField`, `SliderField`, `SelectField`, `SwitchField`, …), `Section` (a card panel; give it an `id` to make it foldable)/`FieldGroup` (related fields in a titled inset box inside a panel)/`Hint`, `PeriodsField` (periods of the day, like a timer's on-times, typed or dragged on a 24-hour strip), `List`/`ListItem`, `CollapsibleSection`, `Tabs`, `RailTabs` (icon tabs on a rail), `PaneHeader`, `ChoiceCards` (pick one of a few cards with pictures), `ChipGroup` (a row of chips, one chosen: categories, a few looks; `size="sm"` in narrow places), `Tooltip`, `Menu` (and `ContextMenu`, which opens at a point), `RenamePopover`, `Dialog` (a panel with a scrolling body, optionally with a main action; dialogs move by their title bar, `useDialogDrag`), `ConfirmDialog`. They wrap Base UI (`@base-ui/react`); don't import Base UI outside the kit, and don't style `<button>`s or inputs by hand. No `title` tooltips, `window.confirm` or `window.alert`: use `Tooltip`, `ConfirmDialog` and `notify()` (`src/editor/toasts.ts`). After changing the kit, check `/kit` (dev only) in both themes.
- **Names say what they hold (fields, keys, identifiers, labels):** a single noun reads like an object, so never use one for a switch, a colour or an amount. Booleans read as a yes/no question or a verb phrase (`showSun`, `showInPerspective`, `castsShadow`, `isOpen`), not `sun` or `dome`; colours say whose colour and where (`colorOverhead`, `colorAtHorizon`, `cloudColor`), not `zenith` or `horizon`; amounts say what they measure (`starDensity`, `cloudCover`, `gradientAngle`), not `stars`, `clouds` or `angle`. Settings that only apply together share a prefix (`gradientStart`, `gradientEnd`, `gradientAngle`), and one field never means two things (a `color` that is also a gradient's start). Avoid words that could mean many things or collide with a later feature (`current`, a bare `traffic` flag). The same goes for inspector labels ("Show the sun in the sky", "Cloud cover", not "Sun", "Clouds"). Ask "what exactly is this, and could a future feature want this name?"
- **Consistent wording:** one idea, one name, everywhere it shows: in option labels, hints, explainer notes, menus, docs and `/schema.json`. If a select offers **From data**, every other select, hint and note says **From data** too (not "By a data value" in one place and "From data" in another), and greyed-out options and the notes explaining them use the same phrase ("no values yet"). Before adding UI text, search for how the same thing is already called (`grep -rn` the label) and reuse it; when renaming one, rename all.
- **Colours are named, not only shown (ADR-0089):** not everyone can tell colours apart. Every colour goes through the kit's `ColorField`, which names it (`describeColor`, and the presets' names in `SWATCHES`); a new preset colour gets a name. Never show state by colour alone: pair it with text, an icon or a shape.
- **Don't hide what isn't available yet:** show options whose precondition is missing greyed out (`SelectField` options take `disabled`), with the reason in the label ("From data (no values yet)") and one note nearby saying how to use the feature, with a button that goes there ("Open the Data tab"). Hidden options can't be discovered.
- **Inherited values (ADR-0027):** a setting that falls back to something else (a default, the scene, the road) is stored as `null` and its field gets an `inherit` prop: the control shows the value in effect, the label row says **Default** / **From scene** while inherited and offers **Reset** once overridden. No "Like the scene…" options inside selects.
- All scene mutations go through the store's `commit()` (or helpers built on it). Pass `{ coalesce: "<stable key>" }` for continuous edits (typing, sliders, drags) so they become a single undo step (ADR-0009).
- Never store runtime/UI state (selection, camera, animation progress) in the scene document.
- Module-level runtime state that mounted components fill (a registry like `drivingVehicles` or the label maps, or progress like the day cycle's) is made with `keepOnHotReload(key, create)` from `lib/hot.ts`, so it survives a hot reload in development; a plain `new Map()` there empties on every code change while the components that filled it stay mounted (vehicles freeze, cards stop following). Caches that rebuild themselves don't need it.
- **Moods (ADR-0078):** a world's moods are full snapshots of its look: the whole `lighting`, `sky` and `water`, and the tilt-shift settings of `camera`. A new field in `LightingSchema`, `SkySchema` or `WaterSchema` is in moods by itself (moods saved before it get its default when put on, so give it one that suits them). A look setting anywhere else (more of `camera`, the backdrop, a new section) goes into them by hand: `MoodSchema` and `moodOf` / `putOnMood` (`scene/moods.ts`).
- **Graphics settings (ADR-0072, ADR-0073):** how much a browser draws (Preferences → Graphics: a preset, Standard / Nice / Ultra, and settings that follow it until changed) lives in `editor/graphics.ts` and the preferences, never in the world; what a world looks like (sun and shade contrast, sky, lights) lives in the world. Standard is the view as it always was and mounts no effects composer: never change its look or cost. A new effect is a setting there (a key in `PreferencesSchema` that is `null` while it follows the preset, its value in each preset, a row on the Graphics page) and a pass in `render/Effects.tsx`, which works in linear light after the scene pass (`SceneAsOnCanvasPass`) and must keep the painted lights' colours.
- In `useFrame`, read `size` (and the camera) from the frame's state (`useFrame(({ size }) => …)`), not from a `useThree` value captured at render: frames can be drawn right after a resize, before React re-renders (ADR-0055).
- Untrusted scene JSON (files, storage, AI) must go through `parseScene()`, or `parseOrRepairScene()` where a partly broken world should still open (ADR-0026).
- Never discard user data. A save that fails to load is kept as a backup and the user is told (ADR-0020). Don't add code paths that overwrite or drop stored worlds without that safety net. The one exception is File → Wipe everything, behind two confirmations (ADR-0045).

## Common tasks

**Add a part:** the `build-a-part` skill (`.claude/skills/build-a-part/SKILL.md`) has the practice: scale, lights, geometry gotchas, what each kind needs, and how to check a part before it's reviewed. Create it with `definePart({...})` in its own file, `src/parts/<category>/<kind>.tsx`, where the folder is its palette category (ADR-0043). Give the Zod schema a default for every prop, list its colours in `colors` (ADR-0060: an id named for what it paints, a name, a default; mark one `legacy: "color"` and a second `legacy: "accent"`, which older worlds and AIs may still write) and draw with `colors.<id>` (giving an existing part another colour: add it with a new id and no `legacy`; never rename or reuse an id, objects store their settings under it); glass with something behind it is a colour marked `seeThrough: { transparency }` (ADR-0090), drawn with an opacity of `1 - transparency.<id>`, which gives it a Transparency slider, describe the inspector controls in `fields`, follow the axis conventions (origin at the footprint centre on the ground, front +Z, vehicles drive +X), then add it to `PARTS` in `registry.ts`. Street furniture is drawn in metres inside `<group scale={UNITS_PER_METRE}>` (`furniture/furnitureSize.ts`: about 1.5 times true scale, so it reads in the miniature), its length props in world units. Add to scene (under its category's chip, a variant on its family's tile, ADR-0088), the inspector and the parts catalogue (`/parts`, ADR-0087) pick it up automatically: check it there in both themes, by day and at night. Objects that look the same are drawn together (ADR-0086): build shapes from three's own geometries where you can, name a geometry built by hand by its shape with `shareGeometryAs` (`primitives.tsx`) so copies of the part share it, and mark a mesh whose material or geometry the part changes in `useFrame` with `userData={{ notInstanced: true }}` (a test checks). A new look for an existing part is a variant with the next number (`race_car_02`, ADR-0050), in its own file; pieces shared by a family's variants go in a kit next to them (e.g. `vehicles/raceCarKit.tsx`, one race car per era of F1), and general shapes in `primitives.tsx` (`Taper` for noses, wedges and fuselages).

**Add a light to a part** (ADR-0058): list it in the part's `lights` (an id, a name, a shape: `lens`, `beam`, `pool`, `windows` or `glow`; default colour, strength, reach for beams and pools, `when: "driving"` for lights only on while driving, and `comesOn`: "atOnce" (the default), "oneByOne" for window lights whose panes light up one after another, or "gradually" to fade in with the dusk, ADR-0061), then draw it in the part's `Component` from `lights.<id>` with the helpers in `parts/lights.tsx` (`lightEmission`, `LightLens`, `Headlights`, `LightPool`, `LitWindows`). A light draws exactly its own colour: for variety, give the part several lights rather than tinting a coloured pattern (the office tower's windows are two lights, Windows and Screens; `LitWindows` gives each of any number of lights its panes by weight, relative numbers that needn't add up to anything, and each light lights its own `litPanes` part of them, so nothing can go over 100%; changing the weights moves whose panes are whose). Name lights for what they are (`screens`), never by number. Never decide on/off or brightness in the part, and never read `palette.night` for lights: `resolveLights` does that from the object's settings, the dark, driving and data. The Lights tab, settings search, data switching and `/schema.json` pick it up. Renaming a light id: add it to `renamedLights`. Moving a setting that used to be a prop into a light: read the old value in the light's `legacy` hook and list the prop in `removedProps`. To let it light its surroundings at night when the graphics settings draw real lights (ADR-0074), give it `realLight(props)`: where it shines from in the part's own space, and a reach for windows and glows (beams and pools use their own); one light per place.

**Make a setting follow data** (ADR-0058, ADR-0060): store a `DataBindingSchema` binding in a map by setting (like a light's or a colour's `data`), read it with `readSwitch`, `readScale` or `readColor` from `parts/dataBinding.ts`, and show it with `DataDrivenField` (Source: By hand / From data, then the hand field or `DataBindingFields`), with a `FollowDataNote` at the top of the tab. A new place that keeps bindings goes in `bindingMapsOf` (`scene/dataBindings.ts`), so data renames and deletes and redrawing on a value change cover it. For a light, add the setting to `LIGHT_DATA` in `parts/lightModel.ts` and read it in `resolveLight`; for a colour, `resolveColor` in `parts/colorModel.ts`. Never add a one-off `…Key` field: the map keeps saved worlds valid. New binding options get defaults (null = a documented default).

**Add or change a part prop** (e.g. balconies on the office tower; ADR-0056): saved worlds have no value for a new prop and keep their old values for changed ones, so:
1. Before changing the format, save today's world as an old world if no fixture covers the current format: `pnpm fixture:old-world HEAD brightwater` (or the template that uses the part).
2. Give the prop a default that draws existing worlds as they were (balconies off, not on), and an inspector field if it's editable.
3. Don't tighten a limit or drop an option old worlds may use.
4. Renaming a prop: list it in the part's `renamedProps` (old → new). Renaming it again: point every older name at the newest, oldest first (`{ pulse: "flashes", pulses: "flashes" }`). Removing one: list it in `removedProps`. Never take entries out of either.
5. Run `pnpm test`: the part guards, `scene/jsonSchema.test.ts` and `scene/oldWorlds.test.ts` say what's wrong.
6. Look at an old world in the browser to check it looks the same.

**Change the scene format:** edit `schema.ts` with defaults for new fields, and give each one a `.describe()` saying what it means (it's what `/schema.json` shows people and AIs writing worlds; ADR-0034). While the app is an experimental playground, change the schema in place: don't bump `SCENE_VERSION` or write migrations. Old saves and files are repaired on load instead (ADR-0026): invalid fields fall back to their defaults and unreadable items are left out, so give new fields sensible defaults. Renaming a field: add the old name to the renamed-field tables in `src/scene/legacy.ts` (ADR-0071), or it silently loses its value; renamed again, point every older name at the newest, oldest first; never remove an entry. Save an old world first (`pnpm fixture:old-world HEAD <template>`) and let `pnpm test` check it still opens with nothing lost (ADR-0056); a field without a default fails the tests unless it's added to the short allowlist in `scene/jsonSchema.test.ts`. Renaming a part kind, road style or area type is fine: add the old id to `src/scene/legacy.ts` so old worlds keep it (ADR-0053). Once worlds need a compatibility promise, breaking changes bump the version and migrate in `migrate.ts`, with a test. Write an ADR if the change is conceptual.

**Add a setting to the properties:** put it in a panel (`Section` with an `id`, an icon and search `keywords`) in the tab it belongs to, or add a tab to `WORLD_TABS` in `Inspector.tsx` or to `entityTabs`/`roadTabs`/`areaTabs` (ADR-0054). Fields made from the kit are found by the settings search automatically. A part's own panels (its shape, colours and lights) are `ui/PartSettings`, shared with the parts catalogue (ADR-0087): they take an object's settings and an `onChange`, so keep the editor's store out of them.

**Add a template:** add a `create…Scene()` in `src/templates/` and register it in `templates/index.ts`. A variant of an existing template (the same world at dusk, say) is `deriveTemplate(createBrightwaterScene, (scene) => { … })` from `templates/derive.ts`: it builds the base fresh and changes only what differs, so later changes to the base flow through; never copy a template's code. The schema test validates every template automatically, and it appears as a starter in File → New world…, with a picture rendered from the template itself (ADR-0047).

## Verifying visually

Unit tests don't cover rendering. UI changes are checked in a real browser: the end-to-end suite in `e2e/` (ADR-0069) runs the editor in Playwright's headless Chromium, one spec file per area (selection, transforms, roads, camera, properties, clipboard, worlds, …), and is also how an agent checks a change by hand.

**Running it.** `pnpm e2e` (all, about 6 minutes with 3 browsers) or `pnpm e2e e2e/roads.spec.ts -g "points"` (one file, or tests by name). It uses the dev server on http://localhost:3000 if one answers (`E2E_BASE_URL=http://localhost:3002` for another, e.g. a worktree's) (the owner's usually does: use it, never kill or restart it), else starts one. It uses the full Chromium build in its new headless mode with SwiftShader for WebGL (`playwright.config.ts`); if Playwright says the browser is missing, `pnpm exec playwright install chromium`. On a bare WSL/Ubuntu machine Chromium may miss `libnspr4`, `libnss3` and `libasound2t64`: without sudo, `apt-get download` them, `dpkg -x` each into a scratch dir, and run with `LD_LIBRARY_PATH` pointing at its `usr/lib/x86_64-linux-gnu`. After many edits to `editor/store.ts`, hot reload can leave modules holding the old store (e.g. every camera key dead): reload the page; it never happens to users.

**Writing tests.** Import `test`, `expect` and the helpers from `e2e/editor.ts`, and reuse or add helpers there rather than repeating code in a spec. Each test gets a fresh browser context (empty storage), so the app opens the starter world (Brightwater) in Edit mode, and fails on any uncaught page error.
- `openEditor(page)`, then set up through the store and check results in it rather than in pixels: `act(page, (s) => s.select("a"))` runs code with the editor's state (its actions; the function runs in the page, so pass values as its second argument), `read(page, (s) => s.selectedItems)` reads it. They reach the store through `globalThis.__editorStore`, which the dev server keeps there.
- `loadWorld(page, { entities, roads, areas })` replaces the starter's things with a small test world (missing fields get defaults); `showView(page, [x, z], span)` sets an exact camera view. Look from close up (a span of about 30): the transform gizmo is always the same size on screen, and from far away it covers neighbouring objects and catches presses meant for them.
- `screenOf(page, [x, height, z])` / `groundSpot(page, [x, z])` say where a world point is on screen, from the live camera (`globalThis.__editorView`, development only): click objects, road points and area corners there exactly, never at guessed pixels. `cameraPose(page)` reads the live camera once it has settled (glides and key moves ease out).
- UI lookups: `outlinerRow`, `labelCard` (cards are buttons in the label layer; outliner rows are buttons too, so don't look cards up page-wide), `menuItem` (any kind of menu item, by text, which includes its description: anchor patterns, e.g. `/^Paste(?! schedule)/`), `pickFromMenu`, `fileMenu`, `choose` (a select field's option), `openPanel` (unfold a panel that starts folded), `keys`, `hold`, `clickWith`, `saved`, `reopened`. Inspector inputs, tabs, switches and search boxes have accessible names (`getByRole("textbox", { name: "Rotation", exact: true })`, `getByRole("tab", { name: "Look" })`).
- Keep it fast: one test per user-facing flow, not per option; logic belongs in unit tests.

**Input gotchas.**
- `page.mouse.click()` ignores a `modifiers` option (only locator clicks take it): use `clickWith(page, ["Shift"], x, y)`, or `keyboard.down` / `up` around a drag. `keyboard.down` takes one key, so `hold` splits combinations.
- Hover the view before editor keys, and move with `{ steps: n }` so pointer moves fire (a move to where the mouse already is fires nothing).
- Things that wait: a menu's Paste reads the clipboard asynchronously (use `expect.poll`), glides take most of a second, and the camera menu stays open while its choices are flipped. The clipboard needs `context.grantPermissions(["clipboard-read", "clipboard-write"], { origin: "http://localhost:3000" })`.
- The starter world has viewpoints, data values and objects of its own: count relative to what's there, or `loadWorld` first. The world's title covers the view's top-left corner, so start box drags below it.

**A quick look while working.** For a screenshot or a one-off check, write a temporary `e2e/debug.spec.ts` with the same helpers (`page.screenshot({ path })` into your scratchpad, `console.log` to see values), run it with `pnpm e2e e2e/debug.spec.ts`, look at the picture, and delete the file afterwards.

**The look and cost of the 3D view** (lighting, graphics settings, the effects composer): `scripts/shots.mjs` takes pictures of the view in View mode for any preset, preference or world setting, at set times of day and views, and measures GPU time per frame (WebGL timer queries); `node scripts/shots.mjs sheet <out> <shot>…` puts shots side by side. On WSL run it with Windows' node (`node.exe scripts/shots.mjs …`): it drives the installed Chrome headless on the real GPU; with Linux's node it uses SwiftShader, whose pictures are right but whose times mean nothing. Compare against Standard: with no effect on, the composer must draw the same picture. The script's header lists its options; shots go to the ignored `shots/` folder. The README's gallery (`docs/gallery/`) is a list of its runs in `scripts/gallery.mjs`: `node.exe scripts/gallery.mjs` retakes it after a change to the look.

## Commits and PRs

Never add AI attribution: no `Co-Authored-By: Claude …` (or any other AI) trailer, no "Generated with Claude Code" line in commit messages or PR descriptions. Commit as the configured git user only. Don't hard-wrap commit message bodies; use one line per bullet. Never commit or push without the owner's explicit go-ahead, every time. Pushing to `main` deploys to production (Cloudflare is connected to the repo).

## Recommending a fresh start

When a release changes the app so much that people are better off starting over (old worlds or settings would get in the way), bump `FRESH_START` in `src/editor/wipeOffer.ts` (ADR-0059). Every browser that has worlds and hasn't seen the new number is offered, once, to start fresh (File → Wipe everything's two confirmations, with Save to file) or carry on. Worlds must still open after the update (ADR-0026, ADR-0056); this is a recommendation, never a replacement for repairing old worlds. Only bump it with the owner's go-ahead.

## ADR workflow

Write a new ADR (copy `docs/adr/template.md`, next free number) for anything that changes structure, dependencies, data formats, conventions or system-level behaviour, and add it to the index table in `docs/adr/README.md`. Don't edit accepted ADRs; supersede them with a new one.
